# Collection imports (H2B-B)

Provenance record for every collection file vendored from an external producer. One
row per import, appended — never rewritten. The imported file itself is a
**byte-identical** copy of the producer's payload; the SHA-256 below is what
`scripts/import_collection.py --expected-sha256` enforced and what
`tests/parity.mjs` section J re-checks on every run, so a silent edit to a "verified"
passage cannot pass unnoticed.

The contract these files conform to is `docs/architecture/COLLECTION_CONTRACT.md`
(accepted as `docs/DECISIONS.md` D27). Built-in collections are not imports — they are
generated by `scripts/build_collections.py` from this repo's own canonical raw corpus.

Notes carried from the producer handoff, not papered over (its "contract friction" §90):

1. The producer's CSV column is `verification_status`; the contract's field is
   `verification_state`. The mapping is applied **at export time on the producer side**,
   so this repo only ever sees `verification_state` (D28, decision 4).
2. `tags` is a comma-separated string in the producer's CSV and an array on the wire —
   transformed by the producer's exporter, not here.
3. The producer's CSV has no `source_url` column yet; `source_url` therefore comes from
   the producer's export mapping, not from its raw rows.
4. The producer export contains 4 items, not the 5 the owner approved, because donor
   `30` failed verification and substitution was forbidden.
