WHAT PROBLEM THIS SOLVES
------------------------
Not what C9 first claimed. C9 was filed as "the Badíʿ date never resolves on the live site"
and that claim was withdrawn (see the CORRECTION section above and docs/queue.md C9). The
date works for anyone who has granted location and for every returning visitor, because the
vendor caches a granted location in localStorage and reuses it.

The real, narrow defect: a FIRST-TIME visitor who DECLINES the browser's location prompt
got no Badíʿ date at all. Mechanism, from the vendor source (BadiDateToday.v1.js v1.09):

  - locationMethod askForUserLocation (3): navigator.geolocation.getCurrentPosition with a
    3000 ms timeout; on failure it sets locationMethod = guessUserLocation (2) and retries
    (vendor lines 552-561);
  - guessUserLocation (2) requests http://ipinfo.io/geo?json (vendor line 573) -- plain
    http, so on an HTTPS page the browser blocks it as mixed content;
  - that XHR sets ontimeout but has NO onerror (vendor lines 575-586), so a blocked
    request fires no handler at all and the library never continues.

The vendor therefore cannot recover by itself, and the page's only rescue was our own 4 s
guard in js/badi-init.js, which rendered "Badíʿ date unavailable.". Our guard is
load-bearing for a vendor failure mode.

THE FIX (option (a))
--------------------
Keep the location-accurate path, and downgrade instead of failing. If the accurate attempt
has not answered within the 4 s guard, re-invoke the library with ignoreLocation, which uses
the default 6:30 sunset and needs no network and no permission -- so the date always renders.
A second call is safe: the vendor reinitialises its own localSettings per call, so a retry is
an independent instance, and our `settled` flag means whichever attempt answers first wins
and the other is ignored.

Implementation notes worth knowing before anyone "simplifies" this file:
  - the caller (not the library) owns the timeout, because every vendor failure path here is
    silent -- there is nothing to listen for;
  - the two wait windows are now named constants: BADI_ACCURATE_TIMEOUT_MS (4000, unchanged
    value, renamed for clarity) and BADI_IGNORE_TIMEOUT_MS (2000 for the no-network retry);
  - the early return when BadiDateToday is absent is unchanged, and remains what section F's
    "unreachable library" test exercises.

THE DOUBLE-INIT CHECK (the caveat raised before implementing)
-------------------------------------------------------------
Re-invoking a third-party initialiser was the one real risk, so it was verified before the
work, not after. Against the live origin with geolocation NOT granted, once the first call
had stalled: a second call with locationMethod 1 returned cleanly, threw nothing, fired
onReady, and reported a valid date (bDay 4, bMonthNameAr "`Izzat", bYear 183).
Confirmed in the source too: `var BadiDateToday = function (settings) { var localSettings = {}; ... }`
-- each invocation gets its own closure, and only localStorage is shared.

GATE 3 — real-vendor end-to-end over TLS (nothing stubbed)
--------------------------------------------------------------------------------
Why TLS: the declined-location failure only exists on an HTTPS page, because the vendor's
ipinfo request is plain http and the browser blocks it as mixed content. A local http://
server would let that request through and prove nothing. So the worktree was served over TLS
with a self-signed cert (Playwright ignoreHTTPSErrors), and the vendor script still loaded
from https://wondrous-badi.today. The browser's geolocation permission was the variable:

The A-vs-B day difference (4 vs 3) is the semantics working as intended, not a discrepancy:
the downgrade uses the library's default 6:30 sunset, while B and C use a real location
(Calgary). Same instant, different sunset, so the Badíʿ day boundary falls differently. That
difference is itself evidence that the downgrade is a genuine fallback and not a no-op.

NOT DONE, STATED EXPLICITLY
--------------------------------------------------------------------------------
- The 4 s accuracy window is unchanged. A declined-location visitor waits ~4 s before the
  date appears. Shortening it would change behaviour for the accurate path too (a slow but
  permitted geolocation could be cut off), so it is left alone; the guard's value is now a
  named constant if that trade is ever revisited.
- The vendor library itself is untouched. Its missing onerror and its plain-http ipinfo
  fallback are upstream defects; option (a) works around them rather than fixing them, which
  is why the fallback can never be shorter than the guard.
