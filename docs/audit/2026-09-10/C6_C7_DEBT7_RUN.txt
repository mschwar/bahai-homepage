C6 — the copy affordance is visible again
--------------------------------------------------------------------------------
css/style.css: `.quote-actions{display:none}` became `display:flex` with the same
gap/wrap/margin treatment as the sibling `.status-row`. The clipboard handler, the status
element and both fallbacks in js/script.js were already present and are untouched: the row was
designed and built, and only CSS hid it.

DEFECT FOUND DURING VERIFICATION, AND FIXED — the first attempt restored the row but the button
was INVISIBLE, so C6 was not actually satisfied. Measured, not guessed:

  before the correction:  label rgb(239,235,233) on rgb(239,235,233)  ->  contrast 1:1
  after the correction:   light 12.85:1 ; dark 12.85:1

Cause: `.button-inline` (line 48) sets `color: var(--text-color); border-color: var(--text-color)`
— which is the theme-correct ink, #1A2639 on the cream jumbotron and #EFEBE9 on the navy one.
But `.button` (line 69) is declared LATER at equal specificity, so it won, applying
`--panel-buttons-text` / `--button-border` — a palette designed for the DARK `.panel-buttons`
date band — to the LIGHT jumbotron. The result was a white-on-white rectangle: a control that
occupied 120x45 px and could not be seen.

Correction: the selector is scoped to `.quote-jumbotron .button-inline` (specificity 0-2-0),
so it wins over `.button` in both themes and `--text-color` resolves correctly per theme. One
selector change, no new variables, no markup change. Applies to all three inline buttons, which
all live inside `.quote-jumbotron` sections (#copy-button, #copy-button-yesterday, #retry-button).

WHY THE FIRST PASS MISSED IT — recorded because it is the useful lesson. The first attempt's
verification asserted the row was not `display:none`, that the row and button had non-zero
boxes, and that the button was enabled. Every one of those is true of an invisible white
rectangle. A presence/size check cannot see colour. The first visual check was what caught it,
and it was then confirmed objectively by measuring contrast rather than trusting either signal.

--------------------------------------------------------------------------------
C7 — the body carries exactly one theme class
--------------------------------------------------------------------------------
js/script.js now removes both `light-mode` and `dark-mode` before adding the saved (or default)
class:

  document.body.classList.remove('light-mode', 'dark-mode');
  document.body.classList.add(savedTheme || 'light-mode');

Previously `index.html` hardcoded `<body class="light-mode">` and the script appended, so a
reload to a saved dark theme left BOTH classes on the body, with the effective theme correct
only because `dark-mode` happened to win on CSS specificity. `index.html` is untouched; the
requirement was exactly one theme class at the end, not a redesign.

--------------------------------------------------------------------------------
tech-debt #7 — the Badíʿ-day cache write is gone
--------------------------------------------------------------------------------
js/script.js no longer executes `saveCachedQuote(pendingBadiKey, todayObj)`, and the
`pendingBadiKey` variable is removed. Nothing ever READ the Badíʿ-day key, and that write could
leave a mismatched verse to be served on a later Badíʿ cache hit if the date boundary shifted —
user-visible wrong text on a product whose doctrine is one passage per day. The Gregorian key is
now the only authoritative read source.

`js/badi-init.js` still supplies the Badíʿ key to the `onReady` callback (its `succeed()` passes
`buildBadiKey(di)`). That is left deliberately: the key is part of badi-init's callback contract
and removing it would be an unnecessary change to a file this batch does not otherwise touch. The
consumer simply no longer uses it, which the in-code comment states.
